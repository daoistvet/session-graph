# ADR 001 — CAG (Compounding Agents) extraction: retired

- **Status:** Removed (dead in production 2026-03-25, removed 2026-07-17)
- **Supersedes:** commits `b3a3a1a`, `a9ce696`, `d5b8be9`
- **Scope:** `pipeline/cag_extraction.py`, `pipeline/cag_cache.py`, CAG wiring in `docker/queue_consumer.py`

This record exists so the intent is not lost and the idea is not relitigated. CAG is
closed. It is not a backlog item.

## What it was meant to do

DevKG answers *what relates to what* — `uses`, `dependsOn`, `enables`. It deliberately
does not capture **why**. CAG was the second half of that idea: a parallel extraction
pass over the same session transcripts that captured engineering *reasoning* —
decisions and their rejected alternatives, failed attempts, observations, and pending
work — and stored it in a separate graph owned by the `compounding_agents` project.

The goal was a future agent that could ask "what was decided here, and what did we
already try and reject?" instead of rediscovering dead ends. `/cag-sparql` was the
query surface; `/devkg-sparql` remained the technical-relationship surface.

### Vocabulary

Six predicates, deliberately closed-world (mirroring devkg's design):

| Predicate | Meaning |
|---|---|
| `decided` | Chose X over alternatives |
| `rejectedBecause` | Why an alternative was rejected |
| `failedWith` | Something was tried and failed |
| `observed` | A learning or insight discovered |
| `blockedBy` | Progress blocked by an issue |
| `nextStep` | What remains to be done |

Triples were typed `decision` / `observation` / `failure`. Decisions additionally
carried `selectedOption` and `rejectedOptions` — the part devkg structurally could not
express.

### Architecture

CAG was **bidirectional**, not merely an exporter. `queue_consumer.py` touched the
`compounding_agents` server (`CAG_SERVER_URL`, default port 4000) at four points:

1. **GET `/api/session-context/{sid}`** — correlate a pipeline job with an orchestrator
   session, writing `devkg:hasCorrelationId` onto the session node **in the devkg graph**
2. **Extract** — a separate LLM prompt, run in a `ThreadPoolExecutor` alongside devkg
   extraction; incremental (last-assistant-message only), with `cag_cache.db` holding
   prior triples per session so the model returned a refined complete set each turn
3. **POST `/hooks/cag-triples`** — write the triples (`replace=True`, whole-session swap)
4. **POST `/hooks/pipeline-complete`** — notify with devkg/CAG triple counts

## Why it is dead

**The store was never owned by this project.** CAG triples did not go to Fuseki. They
were POSTed to a server in a *separate repo* (`compounding_agents`) that had to be
running on port 4000. This project could ingest sessions perfectly and still lose every
CAG triple, which is exactly what happened.

**It failed silently by design.** All four touchpoints swallowed errors as non-fatal —
three of them (`session-context`, `pipeline-complete`, and the executor's `cag` branch)
caught bare `Exception` and passed. `post_cag_triples` logged a `WARN` and returned.
The job then reported `[DONE] ... (4441 devkg + 45 cag triples)` — a success line
quoting a triple count for triples that were never stored. Nothing escalated. Nothing
alerted.

**So it died unnoticed on 2026-03-25 and ran dead for ~4 months.** Two independent
signals agree on the date: the newest timestamp in the `/cag` dataset
(`2026-03-25T12:49:46.985Z`) and the newest session carrying `hasCorrelationId`
(`2026-03-25T12:33:39.636+00:00`). Discovered 2026-07-17 during a production audit, by
which point the consumer was still spending one LLM call per session on extractions
that were thrown away, then reporting success.

**The data it did produce shows quality problems.** Of 18,126 triples: 875
`SoftwareArtifact`, 832 `KnowledgeTriple`, 120 `Alternative`, 94 `Decision` — and 160
instances typed `http://server/unset-base/undefined`, an unset-base-URI bug. The commit
history is a sequence of corrections rather than convergence: `b3a3a1a` (incremental
extraction), `a9ce696` (tighten prompt — reject generic subjects and tautological
observations), `d5b8be9` (eliminate catastrophic triple wipe). The `replace=True`
whole-session swap combined with an LLM that could return `[]` was a data-loss shape
that needed a code-level guard to contain.

## The real lesson

The failure was **architectural, not incidental**. A pipeline stage whose only sink is a
process in another repo, wired to fail non-fatally, is indistinguishable from a stage
that does nothing — except for the cost. It burned tokens and printed a success line for
four months. If a future stage has an external sink, the correct default is: **fail the
job, or don't run the stage.** A `WARN` in a log nobody reads is not error handling.

## What was removed (2026-07-17)

- `pipeline/cag_extraction.py`, `pipeline/cag_cache.py` — deleted (recoverable via git)
- `docker/queue_consumer.py` — all four touchpoints, `CAG_SERVER_URL`, `post_cag_triples()`,
  `_run_cag()`, and the now-pointless `ThreadPoolExecutor` (devkg now runs directly).
  `extract_last_assistant_text()` (~75 lines of per-platform JSONL parsing) went with it —
  it had no other caller.
- `docker-compose.yml` — `CAG_SERVER_URL` env var
- Fuseki — the three empty `cag-test-*` datasets (`handoff`, `integration`, `injection`)
- `pipeline/cache/cag_cache.db` — 735 rows of operational scratch
- `~/.claude/skills/cag-sparql/` and its row in the global `CLAUDE.md` skills table —
  the skill queried a dataset frozen in March and would otherwise keep answering from it

## What was kept and why

- **Fuseki `/cag` — 18,126 triples, frozen.** Read-only archive. Not reproducible: the
  server that wrote it is gone. Kept as evidence of what CAG actually captured.
- **149 `devkg:hasCorrelationId` triples in the live devkg graph.** Orphaned pointers to
  a dead orchestrator, all pre-2026-03-25. Harmless historical provenance; purging them
  would mutate the production graph for no gain.
- **The `compounding_agents` project itself.** A separate repo, out of scope here. This
  ADR only removes *this* project's dependency on it.
